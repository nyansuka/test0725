# データ選別と改善ループ計画

最終更新: 2026-08-02  
親計画: [PLAN.md](./PLAN.md)  
対象: UMANOTE（JRA・高配当候補選別）  
結果レビュー・改善棚卸し: [IMPROVEMENT-PLAN.md](./IMPROVEMENT-PLAN.md)

製品方針は固まった前提で、ここからは **(A) 何を取るか** と **(B) 予想→結果でどう回すか** を決める。

---

## 1. 目的

| 目的 | 意味 |
|------|------|
| データ選別 | 「欲しい」と「選別ロジックに必須」を分離し、自動取得できないものは手動／ルール／後回しを明示する |
| 改善ループ | 当日の候補スナップショットと確定結果を突合し、閾値・因子・Scorer を短い周期で直す |

成功の目安（当面）:

- レース日ごとに「発走前候補」と「確定結果」が同じ `raceId` で突合できる
- 週次で再現率・適合率・候補件数・（任意）仮想回収率が出せる
- 変更は「閾値」「重み」「因子定義」「Scorer 差し替え」のどれかを明示して1つずつ入れる

---

## 2. データの三分類

各項目を次の3軸でラベルする。

| ラベル | 定義 |
|--------|------|
| **必須 (Need)** | ゲート／表示／検証のいずれかが欠けると成立しない |
| **欲しい (Want)** | スコア精度や説明性が上がるが、無くても製品は動く |
| **後回し (Later)** | 価値はあるが Phase 初期の対象外 |

加えて取得可否:

| 取得 | 定義 |
|------|------|
| **Auto** | 既存／拡張の fetcher で取れる（公開 Web・API） |
| **Derive** | 自動取得データからルール算出できる（真値ではない） |
| **Manual** | 人が入れる／外部メモ／視聴メモなど。自動不可またはコスト高 |
| **Unavailable** | 公開されず、当面取れない |

## 3. データ一覧（選別表）

### 3.1 必須 · 自動取得（Need × Auto）

選別ゲート・ボード・検証の土台。**最優先で欠損ゼロを目指す。**

| データ | 用途 | 現状 | メモ |
|--------|------|------|------|
| 開催日・会場・R・発走時刻 | 一覧・横断 | 取得済 | |
| raceId / sourceRaceId | 紐付け・結果突合 | 取得済 | |
| レース条件（芝ダ・距離・クラス名） | 表示・適性 | 取得済 | クラス細分はタイトル依存 |
| 天候・馬場 | 表示・conditionFit | 取得済 | 発走直前に変わりうる |
| 出走馬（馬番・枠・馬名・騎手） | 候補・結果突合 | 取得済 | |
| 単勝オッズ | ゲート・valueGap | 取得済 | |
| 複勝オッズ（上下） | ゲート | 取得済 | |
| 組み合わせ券オッズ（閾値以上） | 全券種ゲート | 取得済（≥8 で間引き） | 閾値変更時は取得下限も見直す |
| 確定着順・払戻 | 検証・日記突合 | ポーリング取得済 | 公式との照合は運用ルール |

### 3.2 必須 · 導出（Need × Derive）

公開の「正解スコア」は無い。**説明可能なルールで仮置きし、ループで直す。**

| データ | 用途 | 現状 | 方針 |
|--------|------|------|------|
| `placePotential` | Soft Score | Scorer 出力 | 差し替え可能な唯一の入口 |
| `factors.*` | 説明・重み調整 | **合成値**（オッズ等から仮生成） | 真の適性データ接続まで「仮」と明記 |
| `relatedPlacePotential` | 買い目評価 | 合成（平均／下限） | 合成方式も検証対象 |
| 短評 `comment` / rationale | 根拠表示 | ルール文 | 因子トップから生成で可 |
| ラベル（注目穴／抑え／見送り） | UI | 閾値で決定 | ラベル境界も検証対象 |
| レース期待度 S〜D | レース単位 | 候補から算出 | 候補品質のサマリ指標 |

### 3.3 欲しい · 自動 or 半自動（Want × Auto/Derive）

スコアの中身を「仮」から「根拠付き」に上げる候補。**必須が安定してから1指標ずつ。**

| データ | 用途 | 取得見込み | 優先 |
|--------|------|------------|------|
| 前走着順・人気・タイム | formSignal | **取得済**（`--enrich-form` / `--with-form`） | 高 |
| 上がり3F・通過順位 | 脚質・展開 | 成績ページ | 高 |
| 脚質ラベル（逃先差追） | paceFit | 傾向ページ or 前走から推定 | 中 |
| コース別成績（同場同距離） | courseFit | **取得済**（同条件ベストタイム＋平均着順） | 中 |
| 騎手・枠のコース傾向 | gateJockey | 公開統計 or 簡易集計 | 低〜中 |
| オッズ時系列（締切直前） | ゲートの再現性 | 複数スナップショット保存 | 中（検証用に重要） |
| 人気順位 | 乖離・分析 | オッズから導出可 | 高（簡単） |

### 3.4 欲しいが自動困難（Want × Manual / Unavailable）

ループの「人間入力レーン」か、日記・メモに閉じる。**選別スコアの必須入力にしない。**

| データ | 用途 | 扱い |
|--------|------|------|
| パドック気配・気配値 | 当日補正 | Manual。日記 `note` または当日メモ。Scorer 入力に混ぜない（初期） |
| 厩舎・調教評価の主観 | 根拠補強 | Manual / 予想家メモ |
| 参考予想家の推奨買い目 | 比較・日記 | Manual（`/journal`）。選別スコアとは分離（PLAN 通り） |
| 自分の購入・実払戻 | 回収率 | Manual → 後に結果突合で半自動化 |
| 展開の「読み」（逃げ過多など） | paceFit | 初期はルール推定。人の読みはメモのみ |
| 非公開の調教時計・内部情報 | — | Unavailable。扱わない |
| リアルタイム超高頻度オッズ | — | Later（製品方針で初期対象外） |

### 3.5 後回し（Later）

| データ | 理由 |
|--------|------|
| 地方競馬全般 | 製品対象外 |
| 血統詳細・産駒統計の本格取り込み | コスト大。ルール安定後 |
| 機械学習特徴量フルセット | Scorer 差し替え Phase で再定義 |
| 天候・馬場の予報時系列 | 当面はスナップショット1点で可 |

## 4. 取得方針（実務ルール）

### 4.1 スナップショットの役割分担

| タイミング | 保存するもの | 目的 |
|------------|--------------|------|
| **発走前（予想スナップ）** | 出走・オッズ板・（あれば）因子入力・`selectLongshots` 出力 | 「その時点で何を推したか」の固定 |
| **確定後（結果スナップ）** | 着順・払戻・公式ステータス | 正解ラベル |
| **突合レコード** | raceId × 候補 × hit / payout | 週次メトリクス |

原則:

1. **改善に使う候補は「発走前スナップ」だけ**（結果後オッズで遡及しない）
2. オッズ閾値を変えて再評価するときは、同じ発走前オッズ板を使う
3. factors が合成のままなら、メトリクスは「製品の挙動」評価であり「真の適性モデル」評価ではない、と注釈する

### 4.2 自動取得の境界

- **入れる:** Need × Auto、および Want のうち fetcher 拡張コストが低いもの（前走・人気など）
- **入れない（初期）:** Manual / Unavailable を無理にスクレイピングしない
- **Derive の扱い:** UI では「ルール推定」と分かる表示にする（`/method` と短評）

### 4.3 優先ロードマップ（データ側）

| 順 | 項目 | 完了条件 | 状態 |
|----|------|----------|------|
| D1 | 発走前候補の日次保存 | `src/data/loop/predictions/YYYY-MM-DD.json`（＋凍結オッズ） | **実装済** (`loop:freeze`) |
| D2 | 結果との突合バッチ | `src/data/loop/evaluations/` に hit フラグ | **実装済** (`loop:evaluate`) |
| D3 | 週次メトリクス表 | Recall / Precision / 件数（`loop:report`） | **実装済（CLI/JSON）** |
| D4 | 前走・同条件タイムの自動取り込み | formSignal / courseFit が合成一辺倒でなくなる | **一部済**（`courseFit`・`formSignal`。`valueGap` は未） |
| D5 | オッズ複数時刻スナップ | 締切直前ゲートの感度分析ができる | 未着手 |

運用コマンド:

```bash
docker compose exec web npm run fetch:jra
docker compose exec web npm run fetch:jra:enrich-form -- 2026-07-25   # 既存スナップに過去走を反映
# フル取得時に同時付与する場合: npm run fetch:jra -- --with-form 2026-07-25
docker compose exec web npm run loop:freeze      # 発走前に一度（オッズが揃ってから）
docker compose exec web npm run loop:evaluate    # 結果後
docker compose exec web npm run loop:report -- YYYY-MM-DD
# 薄い凍結のやり直し: npm run loop:freeze -- YYYY-MM-DD --force
```

注意: netkeiba オッズ API は `action=init` 無しだと発売中でも空になりやすい（fetcher 側で付与済み）。単勝が軒並み `99.9` なら再 fetch → `freeze --force`。

詳細パスは `src/data/loop/README.md`。

## 5. 改善ループ（予想 → 結果 → 調整）

### 5.1 1日の流れ（開催日）

```
[朝〜直前] fetch 出馬表・オッズ
    → selectLongshots（設定固定で実行）
    → 発走前スナップ保存（predictions）
    → （任意）自分／予想家を journal に記録

[発走後] 結果ポーリング（既存）
    → 確定後、当日分を突合
    → 候補 hit / miss、券種別、期待度別の簡易集計

[夜 or 翌週] レビュー（§5.3）
    → 次の変更を1つだけ決める
```

### 5.2 正解の定義（検証ラベル）

PLAN 5.4 を具体化する。**候補の成否は券種の厳密払戻ではなく、関係馬の着順（複勝圏）で見る。**

| ラベル | 定義 |
|--------|------|
| **大当たり (win)** | 関係馬の最良着順が **1着** |
| **馬券内 (place)** | 関係馬の最良着順が **2着または3着**（はずれにしない） |
| **はずれ (miss)** | 関係馬の最良着順が **4着以下**（または着順なし） |
| **ゲート正解集合** | 発走前オッズ ≥ 当時の `oddsThreshold` かつ、上記で馬券内以上 |
| **選別ヒット** | システム候補のうち馬券内以上だったもの |
| **見送りの取りこぼし** | 見送り（または非表示）だったがゲート正解だったもの（再現率の穴） |
| **ノイズ** | 候補に出たがはずれ（適合率の悪化要因） |

券種払戻は仮想回収率の参考に使う。表示ラベルは「大当たり／馬券内／はずれ／待ち」。

指標:

```
再現率 (Recall)  = 選別ヒット数 / ゲート正解集合の件数
適合率 (Precision) = 選別ヒット数 / 確定済みシステム候補数
候補密度         = システム候補数 / レース数
（任意）仮想回収率 = 候補を1点固定投資したとみなした回収率（券種払戻ベース）
```

日記の実回収率は **別レーン**（運用の実感）。選別ロジックの良し悪しは上記の再現率・適合率を主にする。

### 5.3 レビューのリズム

| 周期 | やること | アウトプット |
|------|----------|--------------|
| **毎日（開催日）** | 突合が回ったか確認。明らかな欠損・異常オッズをメモ | 障害メモ（あれば） |
| **週次** | 指標を見る。外れ方のパターンを3つまで言語化 | 「次の1変更」チケット |
| **月次** | 閾値・scoreMin・券種ON/OFFの感度。Scorer 差し替え検討 | 設定デフォルト見直し |

週次レビューの観点（例）:

1. 候補が多すぎる／少なすぎる（密度）
2. 特定券種だけ適合率が極端に悪い
3. 合成 factors に依存した誤誘導（人気だけで加点など）
4. 見送りにゲート正解が溜まっていないか（scoreMin が高すぎ）
5. 期待度 S/A レースの的中が、実際に厚いか

### 5.4 変更の入れ方（1ループ1変更）

同時に触ると何が効いたか分からない。

| 優先順 | 変更種 | いつ触るか |
|--------|--------|------------|
| 1 | `oddsThreshold` / `scoreMin` / 券種ON | 密度・適合が明らかに崩れているとき |
| 2 | related の合成（平均↔下限） | 3連系・ワイドのノイズが多いとき |
| 3 | 因子の重み `WEIGHTS` | 特定因子が常に支配している／無視されているとき |
| 4 | 因子の**定義**（前走データ接続など） | 合成の限界が見えたとき |
| 5 | Scorer 差し替え | 月次でルールの天井が見えたとき |

記録テンプレ（週次チケット）:

```
日付:
対象期間:
指標: Recall=  Precision=  候補/レース=
仮説:
変更（1つ）:
変更しない理由（他候補）:
翌週の見るポイント:
```

### 5.5 人間データ（Manual）のループ上の位置

```
自動レーン: 発走前候補 ↔ 結果  → 再現率・適合率 → Scorer/閾値
手動レーン: journal（自分・予想家） → 実／仮想回収率 → 運用・参考比較
```

- 手動レーンの結果で Scorer を直接学習させない（初期）
- 例外: 「この予想家の切り口をルール化する」と決めたときだけ、Want データとして因子定義に落とす

## 7. 意思決定メモ（初期デフォルト）

議論を短くするための仮決定。違和感があればここだけ覆す。

| 項目 | 仮決定 |
|------|--------|
| **データソース方針（2026-07-25）** | **プラン C:** netkeiba 公開取得＋改善ループを継続。JV-Link / Data Lab / SDK 連携は保留 |
| 検証に使うオッズ時点 | 発走前スナップ（1日1回でも可。余裕があれば締切前もう1回） |
| 組み合わせ券の取得下限 | ユーザー閾値に合わせて動的化（当面は ≥8 のまま運用し、閾値20なら実害小） |
| related 合成 | 当面「下限」（弱い馬に引っ張られる＝穴の過信を抑える） |
| Manual データの Scorer 入力 | 初期は禁止 |
| 日記と選別指標 | 併記するが、改善の主指標は選別の Recall/Precision |

JV-Link はインストール済みでも、HTTP API ではないためサイト直結はしない。精度向上は当面 **開催日の freeze → evaluate → 週次1変更** と、必要なら netkeiba 拡張（D4 前走・人気）で進める。

運用の推奨順（**プラン C**）— 詳細は [SITE-CHECK.md](./SITE-CHECK.md):

1. **開催日・朝:** `fetch:jra` → `loop:freeze`（オッズが揃ってから。薄い凍結は `--force` のみ）  
2. **開催日・定期（〜30分）:** ライブ再 fetch（サイト更新）→ `loop:evaluate` / `loop:trends` → `site:check`（PASS かつ変更ありなら commit / push）。結果ポーリングは `fetcher` が常時担当  
3. **週次:** `loop:report` で Recall / Precision / 密度を見て **変更は1つだけ**  
4. Want から「前走・人気」だけ netkeiba 拡張（D4）。JV-Link は保留
